# 0.1.0 开发预览闭环验收计划

更新日期：2026-09-25。此文件定义接下来每个门槛如何判定通过；已发生的实验与结果仍记录在 [开发预览验收记录](acceptance.md)。当前状态不是发布通过证明。

## 记录规则

每次验收固定一个提交 SHA，记录环境版本、执行命令、退出码、实际观察、失败时的清理结果和证据路径。证据保存在忽略的 `.artifacts/acceptance/<日期-主题>/`，提交到仓库的记录只引用必要摘要，不包含密码、Cookie、设备凭据、完整 Codex 会话或本机项目绝对路径。旧提交上的通过结果不能自动沿用到修改后的安装包。

一次检查只要出现失败、超时、跳过必需步骤，或无法确认清理，就保持“未通过”。替身、独立 Chromium、直接编译产物和演示数据分别注明，不能替代真实宿主、已安装程序和真实服务器的结果。失败后先保存证据和恢复状态，再重试。

## G0：可复现的基础门槛

**目标：**同一提交在本机和 CI 上具有明确的无数据库与真实测试数据库两种结果。

1. 记录 `git rev-parse HEAD`、`node --version`、`pnpm --version`；执行 `pnpm install --frozen-lockfile`。
2. 顺序执行 `pnpm typecheck`、`pnpm lint`、`pnpm test`、`pnpm build`。不设置 `TEST_DATABASE_URL` 时，只有依赖数据库的测试应跳过；不得在测试收集阶段因 `DATABASE_URL` 缺失而报错。
3. 执行 `pnpm test:db`，确认它只使用项目的独立 `*_test` 数据库，数据库集成和安全用例实际运行且全部通过。浏览器验收时另开终端执行 `pnpm exec tsx scripts/test-db.ts --serve`，把它打印的 `TEST_DATABASE_URL` 设在运行浏览器命令的终端，再顺序执行 `pnpm test:e2e` 与 `pnpm test:offline`；结束后停止测试数据库服务。
4. 核对 CI 同一提交的 `verify`、`container` 和 `windows-desktop` 作业结果及产物。平台差异单独记录，不能以本机通过替代 CI 通过。

**通过条件：**各命令退出码为 0；无意外跳过；数据库和浏览器用例有真实执行结果；失败重跑需同时保存第一次失败及诊断。Windows DPAPI 用例单独通过只能定位负载相关超时，不能单独关闭整套门槛。

## G1：受管理 Codex 与安全草稿

**目标：**任务能在已验证的本机项目里打开未发送草稿，任何身份不确定时明确拒绝。

2026-09-25 进展：当前 Codex 版本的独立脚本宿主已通过真实 iframe 内部交互、外部重载与实际 CSP 恢复，以及草稿成功和五类拒绝场景；证据见[验收记录](acceptance.md)。由新安装的 Taskboard 启动器创建进程、私有交接并在该窗口重复完整流程仍待验收，因此 G1 总门槛保持未通过。

2026-09-26 增量：新版 `26.924.1866.0` 隔离宿主与多段落草稿通过；包上下文原生入口、当前用户私有管道及进程句柄交接已实现并实测。重新编译的 Rust release 与 NSIS 安装通过，安装版按钮启动、私有归属探测和重复启动保持同一实例通过。当前等待新隔离窗口登录/选中项目，以继续安装版侧栏、任务草稿及正常退出重启。旧测试版伴随服务的认证关闭未在 15 秒内结束，已记录并清理，不计为正常退出通过。G1 保持未通过。

进程归属的实现与拒绝场景见 [ADR 0003](adr/0003-managed-codex-ownership.md)。

1. 启动器创建独立 Codex 进程，保留进程句柄和独立 profile。实际 PID、创建时间、回环监听端口所有者、精确 `targetId`、页面 URL 和 WebSocket 必须一致；进程退出、端口换主、页面漂移时立即停止接入。环境变量 `TASKBOARD_MANAGED_CODEX=true` 不能充当所有权证据。
2. 在真实宿主版本上验证原生入口、看板 iframe 的 nonce 就绪握手、看板内部交互、“返回 Codex”及重复打开。CSP 启用、失败清理、正常退出和外部重载后，使用实际策略事件确认恢复；无法确认时记录为失败。
3. 对已存在项目证明宿主项目身份与本机目录映射对应。仅在目标项目匹配、唯一编辑器为空、无弹窗时填入草稿；不发送、不领取任务。项目不匹配、已有未发送文字、页面结构变化或会话切换时，原页面保持不变并返回可理解的失败原因。
4. 将上述成功和拒绝场景补入适配器自动回归，再在真实受管理宿主重做。`openThread` 只有在能验证会话路由时才标记可用。

**通过条件：**真实宿主完整执行一次成功路径和所有拒绝路径，记录目标绑定、可见界面、草稿内容、未发送状态及清理结果；主 Codex 实例和其他项目未受影响。版本变化后重新验收宿主标记与项目契约。

## G2：已安装 Windows 程序

**目标：**从同一提交生成的 NSIS 安装包在独立测试账号或测试数据目录完成安装、运行和卸载。

1. 记录安装器 SHA-256、签名状态、安装及卸载退出码。安装后检查随包 Node、WebView2、伴随服务端口和桌面窗口的进程归属。
2. 在已安装窗口设置服务器、登录、创建空间和任务、修改任务、退出再打开并核对数据；记录桌面 IPC、API 响应和界面结果。
3. 验证关闭窗口后的托盘恢复、托盘“退出”后伴随服务及端口释放、再次启动。卸载后检查预期用户数据保留，再重装并核对；只操作专用测试数据。

**通过条件：**所有操作在已安装程序中完成，进程与端口退出后无残留，安装和卸载结果可核对，用户数据行为符合说明。源码组件测试或直接运行 Cargo 产物不算通过。

## G3：两台设备与任务生命周期

**目标：**真实服务器、两台设备和 CLI 完成创建、领取、回写、验收的完整流程。

1. 两台设备登录同一测试空间，设备各自映射同一仓库标识到自己的目录；服务端不接收绝对路径。
2. 设备 A 创建任务，设备 B 观察实时通知和刷新后的版本；在正常测试网络下记录约 2 秒可见断言的实际耗时。断线重连后重新取服务器状态。
3. 使用 `taskctl` 原子领取、提交摘要和验证记录；设备 A 人工验收。验证并发领取只成功一次、版本冲突保留本地草稿、离线只读以及撤权后重新联网清理缓存。

**通过条件：**任务在服务器和两台设备的最终状态一致，所有写入有版本与幂等证据；未发送草稿和离线结果不会被报告为已同步。两秒断言是该环境的验收指标，不是互联网 SLA。

## G4：发布准备

**目标：**只在 G0–G3 均通过后核对发布候选提交。

1. 在隔离环境重跑 Linux Compose、HTTPS、备份恢复和升级回滚。恢复操作只针对测试部署。
2. 核对 CI 由同一提交生成的 Windows 安装包、Linux 镜像、SBOM、SHA256SUMS 和来源证明；逐一验证校验和与版本。
3. 由维护者核对仓库 ruleset、发布环境审批及签名状态，更新 `docs/acceptance.md` 中各门槛的实际证据，再决定是否创建标签或发布草稿。

**通过条件：**产物与验收提交一致，发布记录明确未签名或已签名状态，所有失败和豁免有维护者记录。任何未完成门槛都保持开发预览状态。
